# NetZapret

Диспетчер маршрутизации трафика для Windows: для каждого приложения или домена
выбирает, пустить трафик через десинк (Zapret), через прокси или напрямую.

**Цель — заменить собой связку Zapret GUI + VPN-клиент**, объединив обе технологии
в одном месте. Это значит, что в скоуп входит и управление `winws2.exe` с его
пресетами, и подключение к VPN — а не только решение «кому какой трафик».

## Состояние

| Модуль | Что делает | Готовность |
| --- | --- | --- |
| `NetZapret.Core` | Модель правил, режимы работы, движок сопоставления | Готов, покрыт тестами |
| `NetZapret.Etw` | Наблюдение за соединениями и DNS через ETW | Готов, проверен на живом трафике |
| `NetZapret.Wfp` | Наблюдение через WFP net-events | Работает, но см. ниже — не используется по умолчанию |
| `NetZapret.Cli` | Команды `watch` / `rules` / `test` / `status` | Готов для PoC |
| `NetZapret.Dns` | Статическая карта имён для отладки | Вспомогательная |
| `NetZapret.Subscriptions` | Разбор ссылок и подписок, квота и срок из заголовков | Готов, покрыт тестами |
| `NetZapret.Proxy` | Генерация конфига sing-box из правил и подписки | Готов, проверяется `sing-box check` |
| `NetZapret.Zapret` | Разбор пресетов winws2, сборка его командной строки | Готов, покрыт тестами |
| `NetZapret.Supervisor` | Запуск служб, слежение за живостью, перезапуск | Готов, проверен на обоих движках |

## Как это устроено

Принуждение выполняет **route-движок sing-box**, а не собственный код. NetZapret
владеет правилами и их семантикой, sing-box — исполнением: правила компилируются
в его `route.rules` (`process_name`, `domain_suffix`, `rule_set`), домены
разрешаются через fakeip, серверы переключаются по Clash API без перезапуска.

Своего WFP-callout'а в проекте нет и не планируется в MVP. Кастомная логика
классификации и `ALE_CONNECT_REDIRECT` живут только в kernel-mode драйвере,
который требует WDK, EV-сертификата и attestation-подписи.

### Почему наблюдение построено на ETW, а не на WFP

Изначально `watch` подписывался на net-events WFP. Выяснилось, что на Windows 11
26200 события `FWPM_NET_EVENT_TYPE_CLASSIFY_ALLOW` не приходят вообще: сбор
включён, ключевое слово `CLASSIFY_ALLOW` движком принято, подкатегория аудита
«Filtering Platform Connection» включена — а событий нет, и в журнале
безопасности записей 5156 тоже нет. Доходят только `CLASSIFY_DROP`, по которым
диспетчер маршрутизации не построить.

Поэтому источник по умолчанию — ETW-провайдер ядра: он отдаёт PID, адрес и порт
назначения напрямую и не требует общесистемных настроек. Реализация WFP осталась
доступной через `--source wfp`: интероп рабочий (смещения структур проверены на
живых событиях), и он понадобится для фильтров защиты от утечек.

Доменные имена в PoC берутся из наблюдения за провайдером `Microsoft-Windows-DNS-Client`
в той же сессии. Способ рабочий, но с потолком: браузеры со встроенным
резолвером (Chrome, Firefox с DoH) ходят мимо службы DNS-клиента, и их имён
не видно. Окончательно это решает fakeip на стороне sing-box.

### Сосуществование с Zapret

Наблюдатель строго пассивный: ни одного фильтра WFP не добавляется, ни один
пакет не меняет судьбу. Zapret работает на своём слое WinDivert, и мы на его
пути не появляемся.

Режим `desync` выделен отдельно от `direct` намеренно. Механически сегодня это
одно и то же — мы не трогаем такой трафик, и winws2 обрабатывает его сам. Но
различие важно: когда появится TUN, трафик в режиме `desync` обязан обходить
туннель целиком, иначе десинк будет применяться к переоткрытому сокету sing-box,
а не к исходному потоку приложения.

## Использование

Показать правила в порядке вычисления:

```bash
dotnet run --project src/NetZapret.Cli -- rules --config config/rules.example.yaml
```

Проверить конкретное сочетание, не поднимая WFP (права администратора не нужны):

```bash
dotnet run --project src/NetZapret.Cli -- test --config config/rules.example.yaml --domain rutracker.org
```

Наблюдать за реальными соединениями — **из консоли с правами администратора**:

```bash
dotnet run --project src/NetZapret.Cli -- watch --config config/rules.example.yaml
```

Обзор: что найдено и что готово к работе.

```bash
dotnet run --project src/NetZapret.Cli -- doctor
```

Проверить, что прокси жив и через него идёт трафик. Прав администратора
не требует: поднимается локальный инбаунд, TUN не создаётся.

```bash
dotnet run --project src/NetZapret.Cli -- probe --sub https://example.com/sub/token
```

Запустить службы под присмотром супервизора:

```bash
dotnet run --project src/NetZapret.Cli -- start --proxy-config runtime/singbox.json --verify-traffic
```

Посмотреть подписку — квоту, срок и список серверов:

```bash
dotnet run --project src/NetZapret.Cli -- sub --sub https://example.com/sub/token
```

Собрать конфиг sing-box из правил и подписки:

```bash
dotnet run --project src/NetZapret.Cli -- config --sub https://example.com/sub/token --out runtime/singbox.json
```

Результат сразу проверяется командой `sing-box check`, если движок найден
в `tools/`. Права администратора для генерации и проверки не нужны.
Серверы с транспортом `xhttp` пропускаются — см. [docs/singbox.md](docs/singbox.md).

Ключ `--proxy-only` заводит в туннель только трафик прокси, чтобы десинк
Zapret работал на исходных потоках приложений; `--no-tun` собирает конфиг
с локальным прокси вместо туннеля — он запускается без прав администратора.

### Про права и завершение

Подписка на net-events включает **общесистемный** сбор событий WFP через
`FwpmEngineSetOption0`. Исходные значения сохраняются при старте и
восстанавливаются при выходе, поэтому завершать `watch` нужно через Ctrl+C.
Если убить процесс, сбор событий останется включённым до следующего аккуратного
запуска или до перезагрузки.

### Проверка доменных правил до появления fakeip

WFP отдаёт адрес назначения, но не имя. Пока прокси-движок не подключён,
подставить имена можно вручную:

```bash
dotnet run --project src/NetZapret.Cli -- watch --hosts-map config/hosts.map
```

Без карты доменные правила помечаются в выводе как непроверяемые — это
отличается от «сработал default».

## Режимы работы

Глобальный режим задаётся ключом `mode` в начале конфига и решает, вычисляются
ли правила вообще:

| Режим | Поведение |
| --- | --- |
| `off` | Всё напрямую, правила не читаются |
| `selective` | По умолчанию десинк, прокси включается точечно правилами |
| `proxy` | Весь трафик через VPN, правила не вычисляются |

Локальные сети и loopback остаются прямыми в любом режиме — прописывать их
правилами не нужно.

У `off` пока есть оговорка: сегодня NetZapret гарантирует только отсутствие
прокси — остановить сам десинк он ещё не умеет. Это временно и снимется вместе
с реализацией `NetZapret.Zapret`, после чего `off` начнёт останавливать `winws2`
по-настоящему.

Если секция `default` не задана, она вытекает из режима: `selective` → `desync`,
`proxy` → `proxy`, `off` → `direct`.

## Формат правил

```yaml
rules:
  - match: process
    value: "somegame.exe"
    mode: direct
  - match: domain
    value: "*.rutracker.org"
    mode: proxy
    server: "auto"
default:
  mode: direct
```

`match`: `process` | `domain` | `ip`. `mode`: `direct` | `proxy` | `desync`.

Приоритет — по типу правила: сперва все `process`, затем `domain`, затем `ip`,
затем `default`. Порядок строк внутри одного типа сохраняется. Маска `*.example.com`
покрывает и сам `example.com`.

Полный пример с комментариями — [config/rules.example.yaml](config/rules.example.yaml).
