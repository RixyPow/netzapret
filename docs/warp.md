# WARP: как работал и почему перестал

Написано для того, кто возьмётся чинить. Здесь история целиком, потому что
без неё легко повторить два опровергнутых замером вывода — оба уже были
сделаны, и оба стоили времени.

Всё измеренное датировано. Где стоит «замер» — это замер, а не рассуждение.

---

## Что такое WARP у нас

Бесплатный выход Cloudflare, который **добавляется** к серверам подписки,
а не заменяет их. Пока те живы, автоподбор берёт их — они быстрее; когда
лягут, остаётся он. Роль — запасной выход, который не кончается и не истекает.

Идёт по **MASQUE**: поверх QUIC на 443 порту, оператору неотличим от обычного
трафика. Выключатель — в разделе «VPN», сейчас у владельца **выключен**.

---

## Первая жизнь: выход по WireGuard, убран

Изначально выходов было два. Тот, что по WireGuard, **не мог работать
в принципе**, и это не предположение.

Cloudflare кладёт идентификатор учётной записи в поле `reserved` каждого
пакета. Sing-box 1.14 убрал это поле из настройки пира вовсе — в структуре
остались адрес, порт, ключи, `allowed_ips` и `keepalive`, и положить туда
идентификатор стало некуда.

Проверено на живой сети: рукопожатие проходит, данные не возвращаются
ни на 2408, ни на 500, 4500, 1701, 908. В списке он держался вечным
«не отвечает», а закреплённый по ошибке — обрывал сеть целиком.

Убран вместе со всей обвязкой в `4d2785e`: заведение ключей, регистрация,
разрезанное приветствие и файл `config/warp.json`. Ничего из этого MASQUE
не требует — он делает всё сам, внутри движка.

**Вывод для нового: к WireGuard не возвращаться.** Поле не вернут.

---

## Вторая жизнь: MASQUE работал

**Замер 11.09.2026.** Через Clash API выход отвечал: `warp=on`, `colo=DME`,
`loc=RU`, задержка **437 мс**. Телеграм через него работал, что для владельца
и было признаком живого туннеля.

Тогда же измерена его главная слабость — **неровность под нагрузкой**:

```
один канал, в одиночку      94–188 мс
пять одновременных          281 / 296 / 305 / 932 / 4648 мс
```

Причина в устройстве: один QUIC-канал на все соединения. Отсюда и роль
запасного, а не основного.

### Почему он тогда работал

Движок ходит за учётной записью сам:
`POST https://api.cloudflareclient.com/v0a4471/reg`. Удавшаяся регистрация
ложится в `runtime\engine-cache.db` — за это отвечает `store_masque_config`
в разделе `cache_file`.

То есть 11.09 регистрация **прошла один раз**, и дальше выход жил на записи
из кэша. Ровно в тот день, 11.09 в 20:56 и 22:33, в пресет добавляли рецепт
для домена регистрации — и он тогда сработал.

---

## Как отвалился: две разные поломки, их легко спутать

### 1. WARP утащил за собой весь туннель — **починено**

**Замер 15.09.** В журнале sing-box каждые тридцать секунд:

```
outbound/masque[Cloudflare WARP]: Failed to connect tunnel:
    connect-ip: failed to read response:
    http3: parsing frame failed: timeout: no recent network activity
```

Но беда была не в самом WARP, а в том, что **он оказался выбранным выходом**.
Clash API показал:

```
"name": "auto",  "now": "Cloudflare WARP"
```

При том, что в настройках стояла Польша, и **программа показывала Польшу** —
она читает настройки, а не движок. Весь туннельный трафик шёл через мёртвый
выход: Telegram, Instagram, WhatsApp.

Причина: движок помнит прошлый выбор селектора в своём кэше, а кэш переживает
и перезапуск, и пересборку конфига. WARP залип там с давних проб.

Отключить запоминание не вышло — поле `store_selected` сборка 1.14 не знает
и **отвергает весь конфиг** с FATAL. Поймал это тест, гоняющий конфиг через
`sing-box check`; без него правка унесла бы туннель в выпуск.

Починено в `7110e83`: после запуска движку говорят выбор вслух, через его же
API.

### 2. Регистрация не проходит — **открыто, но WARP это не мешает**

Замер 20.09 в ночь перевернул картину, и ошибку стоит назвать, потому что
на неё ушло полночи.

**WARP работает.** Проверено на копии рабочего кэша владельца: выход
`104.28.230.246`, за ноль секунд, ни одного запроса к `/reg`.

Разница с неудачными заходами — **одно имя выхода**:

```
tag = "warp"               → идёт регистрироваться → TLS handshake timeout
tag = "Cloudflare WARP"    → берёт запись из кэша  → выходит наружу за 0 с
```

Запись в кэше **привязана к имени выхода**. Поставь другое — движок решает,
что учётной записи нет, и идёт за новой. Все мои опыты подставляли чужое имя
и пустой кэш, то есть мерили сломанную перерегистрацию вместо работающего
выхода.

**Что отсюда следует.** Регистрация нужна ровно один раз. Пока кэш цел,
она не запрашивается вовсе, и рецепт под приветствие Go нужен **только
для первого запуска на новой машине**. Для владельца, у которого кэш
от 11.09, WARP исправен.

**Что проверено и совпадает.** Программа собирает ровно то, что сработало:

```
имя выхода   «Cloudflare WARP»            Warp.MasqueTag, не менялось
кэш          runtime\engine-cache.db      CachePath, не менялся с 11.09
              store_masque_config: true
```

Уборка кэш не трогает: и кнопка «Очистить» в «Ещё», и консольная `clean`
удаляют только `.json` и `.log`, а кэш лежит в `.db`.

**Что осталось открытым.** Первый запуск на чистой машине: кэша нет,
регистрация не проходит, WARP не поднимается вовсе. Здесь и нужен рецепт,
выверенный на приветствии Go, — см. ниже.

**Чем проверять, не ломая рабочее.** Поднять свой sing-box с одним выходом
`masque`, именем `Cloudflare WARP` и **копией** кэша, а не самим кэшом:

```json
{ "outbounds": [ { "type": "masque", "tag": "Cloudflare WARP" } ],
  "experimental": { "cache_file": {
      "enabled": true, "path": "…копия…", "store_masque_config": true } } }
```

Пустой кэш в такой проверке означает «мерю первый запуск», полный —
«мерю обычную работу». Спутать их легко, и это стоило ночи.

---

## Почему нельзя обойти

Перебрана схема выхода MASQUE (19.09). Из всех настроек он принимает
**только два поля**: `detour` и `tls.server_name`.

Поля `server`, `server_port`, `license`, `fake_packets` и `tls.utls` движок
объявляет незнакомыми и **отказывается читать конфиг целиком**.

Значит:

- подменить узел регистрации нечем;
- включить uTLS, чтобы приветствие стало похоже на браузерное, нечем;
- направить запрос через другой выход — только через `detour`, но это
  требует живого второго выхода, то есть работающей подписки, а WARP нужен
  ровно тогда, когда её нет.

**Остаётся одно: рецепт под приветствие Go.**

---

## Что это часть большего

Та же беда всплывала в проекте трижды, и стоит держать её в голове целиком.

**Рецепты десинка привязаны к раскладке приветствия, а приветствий у нас три
разных:**

```
Windows / schannel     наша проба блокировок, curl на этой машине
Go                     sing-box
браузерное             Chrome, и его-то и видел автор пресета
```

Рецепт, выверенный на одном, на другом не работает. Отсюда:

- WARP: рецепт под Windows, движок на Go — поток гибнет после рукопожатия;
- проверка блокировок: `twitch.tv` числился закрытым и открывался в браузере,
  `itch.io` числился оборванным и работал. Приветствие .NET не похоже
  на браузерное: другой порядок шифров, нет GREASE, нет ALPN. ALPN пробовали
  добавить — стало хуже.

Чинить WARP рецептом — значит выверить его **на приветствии Go**. Проверять
придётся через сам движок: наша проба даст ответ про свой собственный
ClientHello, а не про его.

---

## Короткий список для того, кто возьмётся

**Прежде всего:** перед любым опытом убедиться, что выход зовут
`Cloudflare WARP`, а кэш — копия рабочего. Иначе меряется первый запуск,
а не работа, и все рецепты дают один и тот же ответ.

**Не делать:**

- возвращать WireGuard — поле `reserved` убрано из sing-box;
- вносить `api.cloudflareclient.com` в исключения десинка — замером отменено,
  без десинка нет даже рукопожатия;
- писать, что домен регистрации закрыт — открывается насквозь;
- добавлять `store_selected` в `cache_file` — поля нет, конфиг отвергается
  целиком с FATAL.

**Где смотреть:**

```
src/NetZapret.Subscriptions/Warp.cs     знание записано в комментариях
presets/Universal V8.txt, секция #6     рецепт домена регистрации
README.md, раздел известных бед         сводка
git show 134c42b                        замер 19.09 целиком
```

**Чем проверять:** `runtime\sing-box.log` — там движок говорит словами,
что у него не вышло. И Clash API на `127.0.0.1:9090` — он единственный
источник правды о том, какой выход **на самом деле** выбран; программа
показывает настройки, а не движок.
