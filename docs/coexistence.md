# Zapret под поднятым TUN: результаты первого замера

Дата: 2026-08-23. sing-box 1.13.19, TUN `netzapret0`, `winws2` с пресетом
Universal V6, режим `selective` (почти весь трафик — `direct`, в прокси уходил
только rutracker.org).

## Что измерялось

TCP-подключение плюс TLS-хендшейк с SNI. Проверять только порт бессмысленно:
DPI обычно пропускает handshake TCP и рвёт соединение на ClientHello.

| Хост | Путь в конфиге | Результат |
| --- | --- | --- |
| `www.youtube.com` | desync → direct | TLS OK, 213 мс |
| `discord.com` | desync → direct | TLS OK, 140 мс |
| `www.google.com` | direct (final) | таймаут 21.7 с |
| `a-api.anthropic.com` | direct (final) | таймаут 21.7 с |
| `rutracker.org` | proxy (selector) | сброс через 5.1 с |

## Главный вывод

Ответ на вопрос «переживает ли десинк поднятый TUN» оказался не «да» и не «нет»,
а **зависит от рецепта**.

Сопоставление с секциями пресета Universal V6:

| Рецепт в пресете | Хосты | Под TUN |
| --- | --- | --- |
| голый `multidisorder` | youtube.com | работает |
| `send:repeats` + `syndata` | discord.com | работает |
| `fake:blob=tls_google:...:tcp_ack=-66000` + `multidisorder` | google.com, claude | **ломается** |

Разделение проходит ровно по наличию `fake`-пакета с подменёнными TTL и ACK.
Рецепты, которые лишь переставляют и режут реальный поток, переживают TUN;
рецепты, добавляющие в поток отдельный поддельный пакет, — нет.

Механизм пока не установлен. Правдоподобное объяснение: `direct`-выход sing-box
переоткрывает соединение собственным сокетом, и подделка, рассчитанная на
относительные номера последовательности и TTL исходного потока, попадает мимо.
Проверять это следует отдельным экспериментом, а не догадками.

## Решение: исключить десинк-адреса из перехвата TUN

У TUN-инбаунда sing-box есть поле `route_exclude_address`. Перечисленные в нём
подсети не заводятся в туннель вовсе — трафик к ним уходит обычным маршрутом
через реальный интерфейс, где WinDivert видит **исходный** поток приложения.
Тогда все рецепты, включая `fake`, работают ровно как без туннеля.

```json
{
  "type": "tun",
  "auto_route": true,
  "route_exclude_address": ["142.250.0.0/15", "87.228.47.0/24", "2a00:1450::/32"]
}
```

Проверено `sing-box check`, код возврата 0. Внимание: поля
`inet4_route_exclude_address` и `inet6_route_exclude_address` — устаревшие,
в 1.12 они удалены, осталось одно объединённое `route_exclude_address`.

Откуда брать список адресов: из самого пресета. Секции содержат `--ipset`
с файлами `lists/ipset-*.txt` — это готовые диапазоны сервисов, которые
пресет чинит десинком.

### Почему одних исключений по адресам недостаточно

Разбор Universal V6 (44 активных секции) показал, чем секции сопоставляют трафик:

| Способ сопоставления | Секций |
| --- | --- |
| только `--ipset` (адреса) | 9 |
| только `--hostlist` (домены) | 34 |

Среди 20 секций с рецептом `fake` — тех самых, что ломаются под TUN, —
**14 сопоставляются только по доменам**: Google, Claude, chatgpt, Gemini,
Notion, DeepSeek, Twitch, EpicGames, Amazon, Steam, i.scdn.co, rutor,
«Мои сайты», Russia blacklist.

`route_exclude_address` принимает только адреса. Он закроет 5 проблемных
секций из 20. Разрешать 117 тысяч доменов пресета в адреса заранее
неосуществимо: CDN отдают разные адреса, списки живут своей жизнью.

### Обратная схема: заводить в TUN только то, что идёт в VPN

Вместо «исключить весь десинк» — «включить только прокси». У TUN-инбаунда
есть парное поле `route_address`: в туннель попадают **только** перечисленные
префиксы, всё остальное идёт обычным маршрутом.

Связка с fakeip делает это точным:

1. Правило DNS выдаёт fakeip-адрес (`198.18.0.0/15`) **только** доменам,
   которые по правилам NetZapret идут в прокси. Остальным отдаётся настоящий адрес.
2. У TUN стоит `route_address: ["198.18.0.0/15"]`.
3. Следствие: в туннель заходит только прокси-трафик. Десинк-трафик туннеля
   не касается вовсе, WinDivert видит исходные потоки, все рецепты работают.

Схема совпадает с моделью пользователя: по умолчанию десинк, прокси точечно.
Чем меньше правил `mode: proxy`, тем меньше трафика в туннеле.

Цена: чтобы выдавать fakeip, sing-box должен видеть запросы DNS, а при
`route_address` только на fakeip-диапазон запросы к резолверу в туннель
не попадут. Значит системный DNS придётся направить на локальный слушатель
sing-box. Известный риск — браузеры с DoH: замер 2026-08-23 показал, что
Chrome резолвит мимо системной службы. Для них потребуется либо отключение
встроенного резолвера политикой, либо опора на sniffing домена из ClientHello.

### Проверено вживую 2026-08-23

Выборочный перехват поднят на реальной машине при работающем `winws2`
с пресетом Universal V6. Результат:

| Проверка | Итог |
| --- | --- |
| `api.ipify.org` (правило `mode: proxy`) | адрес сменился на адрес VPN |
| `google.com` | работает |
| Claude (`api.anthropic.com`) | работает |

Оба последних вчера при сплошном перехвате отваливались: их секции
в пресете используют рецепт `fake`, который туннель не переживает.
При выборочном перехвате их трафик в туннель не заходит вовсе,
WinDivert видит исходные потоки, и десинк работает как без VPN.

Побочное наблюдение: значка сетевого подключения Windows при этом
не показывает — в отличие от клиентов, забирающих маршрут по умолчанию.
Это ожидаемо и является признаком правильной работы режима: маршрут
по умолчанию не трогается намеренно, иначе десинк снова сломается.

### Точечный VPN для приложения — подтверждено 2026-08-23

Конфиг `config/rules.telegram.yaml`: правило `match: process` для
`telegram.exe` с `mode: proxy`, плюс секция `capture` с
`lists/ipset-telegram.txt`.

Результат на живой системе при работающем `winws2` с Universal V6:

| Приложение | Путь | Итог |
| --- | --- | --- |
| Telegram | VPN по правилу процесса | работает |
| YouTube | десинк | работает |
| Discord | десинк, включая голос | работает |

То есть трафик одного приложения уходит в туннель, а всё остальное
одновременно чинится десинком на исходных потоках. Ради этого и затевалось
разведение перехвата.

**Ключевая деталь: одного правила по процессу недостаточно.** Перехват
решается по адресу назначения, а Telegram ходит к своим дата-центрам
по голым IP без обращения к DNS. Fakeip ему не выдаётся, в туннель он
не попадает, и sing-box не доходит до сопоставления процесса — правило
верное и не срабатывает никогда. Диапазоны нужно заводить в туннель явно.

То же потребуется любому приложению без DNS: играм, голосовым чатам,
торрент-клиентам.

## Следствия для проекта

1. **Режим `desync` обязан обходить TUN целиком**, а не полагаться на `direct`
   внутри sing-box. Это перестаёт быть теоретическим соображением: половина
   рецептов пресета под TUN не работает. Различие между `direct` и `desync`
   в модели правил оказалось оправданным.
2. Пока исключения не реализованы, поднимать туннель на этой машине означает
   терять доступ к google.com и API Anthropic.

## Отдельная проблема: путь через прокси

`rutracker.org` через outbound Trojan + REALITY оборвался с «remote party has
closed the transport stream» за 5 секунд. Это не связано с Zapret — не работает
сам прокси. Возможные причины по убыванию вероятности: неверно собранный блок
REALITY (`public_key` / `short_id` / отпечаток uTLS), неподходящий сервер в
селекторе, либо сервер требует параметров, которых нет в модели. Требует
отдельного разбора: включить `log.level=debug` и посмотреть, что отвечает сервер.
