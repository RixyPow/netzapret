## Пункт 1. Прокси — ЗАКРЫТ, работает

**Прокси поднимается, трафик через него идёт.** Внешний адрес меняется:
`81.200.24.34` → `104.171.134.39` и другие, в зависимости от сервера.

Из 14 серверов подписки, пригодных для sing-box, **работают 6**:

| Сервер | Внешний адрес |
| --- | --- |
| Hysteria2 США | 54.156.153.8 |
| Hysteria2 Гонконг | 18.166.162.149 |
| Trojan Гонконг | 18.166.162.149 |
| Hysteria2 США (вход РФ) | 104.171.134.39 |
| Trojan США | 54.156.153.8 |
| Hysteria2 Россия | 104.171.134.39 |

### Как проверять

```
netzapret probe --sub <ссылка>          # по одному серверу каждого протокола
netzapret probe --sub <ссылка> --all    # все серверы
netzapret probe --sub <ссылка> --server Гонконг
```

Код возврата 0, если хотя бы один сервер работает — годится для скриптов
и для супервизора. Прав администратора не требует: поднимается локальный
инбаунд `mixed` на 127.0.0.1, TUN не создаётся, маршруты не трогаются.

Проверка функциональная, а не «порт слушает»: sing-box поднимает инбаунд
раньше, чем выясняет, что до сервера не достучаться. Единственный надёжный
признак — HTTP-запрос через прокси, вернувший чужой внешний адрес.

### Что было сломано на самом деле

Три разные причины, которые я сперва принял за одну.

**1. Ошибка в моём конфиге пробника (исправлено).**
`detour` DNS-сервера в пустой direct-исходящий sing-box 1.13 отвергает:
`detour to an empty direct outbound makes no sense`. Развязка «чтобы разрешить
имя сервера, нужен прокси, а чтобы поднять прокси — разрешить имя» сделана
правилом маршрута по адресу резолвера, а не через detour.

**2. Сетевая блокировка (вне нашего контроля).**
Серверы в Швеции, Германии и Нидерландах недоступны: `i/o timeout` при dial.
Проверено независимо от sing-box — `de.vp.uspn.io` не отвечает по TCP
на портах 4443, 443 и 80. То есть блокируется хост целиком, а не протокол.

**3. Расхождение sing-box и Xray в REALITY (открытый вопрос, см. ниже).**

### Открытый вопрос: VLESS + REALITY не работает в sing-box, но работает в Xray

Два сервера (`Россия`, `США (вход РФ)`) отдают `reality verification failed`
за 30–60 мс: TCP соединяется, падает проверка REALITY на уровне TLS.

Проверено:

* **Xray с теми же параметрами подключается успешно** — внешний адрес получен.
  Параметры брались из моего же сгенерированного конфига sing-box, так что
  расхождения в разборе ссылки исключены.
* Дело не в `flow`: без `xtls-rprx-vision` ошибка та же. Это ожидаемо —
  проверка REALITY идёт на уровне TLS, до того как играет роль flow.
* Дело не в генерации REALITY вообще: **Trojan + REALITY в sing-box работает**
  (Гонконг, США). Ломается именно связка VLESS + REALITY у этого провайдера.

Вывод: sing-box не поддерживает какую-то особенность REALITY на этих серверах.
Правдоподобно — новый вариант аутентификации из свежего Xray.

**Требуется решение пользователя.** Вариант, который я бы выбрал: держать Xray
вторым движком для тех серверов, что sing-box не тянет. Это отменяет мой
прежний вывод «Xray не нужен» — он был сделан до того, как появилась
возможность проверить серверы вживую. Xray уже скачан и лежит в `tools/xray`.

Ничего в эту сторону не делал: решение меняет архитектуру, будить не стал.

## Пункт 2. Супервизор — ЗАКРЫТ для прокси, не тестирован для winws2

```
netzapret start --proxy-config runtime/singbox-local.json --verify-traffic
netzapret status
netzapret stop
```

**Проверено вживую:** запуск, обнаружение убитого процесса, перезапуск
со сменой PID и счётчиком рестартов, глубокая проверка трафика, остановка
всего дерева процессов. Убивал дочерний sing-box вручную — супервизор поднял
его заново за один цикл опроса.

Устройство:

* **Проверка живости двухуровневая.** «Процесс существует» — слабая гарантия:
  sing-box успевает подняться и умереть по существу, оставаясь живым процессом.
  Поэтому у каждой службы есть функциональная проверка. У sing-box это порт
  Clash API, а с `--verify-traffic` ещё и настоящий запрос через прокси
  раз в несколько циклов: порт может слушаться, когда трафик уже не идёт.
* **Перезапуск с удвоением задержки** и лимитом попыток. Лимит обязателен:
  без него неверный конфиг превращается в бесконечный цикл запусков,
  который со стороны выглядит как работающая система.
* **Три подряд неудачные проверки** до перезапуска, а не одна: разовый промах
  бывает от сетевой икоты, и перезапуск прокси из-за неё делает хуже.
* **Состояние в файле** `runtime/supervisor.state.json`. `start`, `stop`
  и `status` — три отдельных запуска программы, а служба Windows потребовала бы
  прав администратора.

**winws2 не тестирован.** Код написан (`WinwsService`, `WinwsCommandLine`),
командная строка собирается из пресета со всеми аргументами как есть, включая
`--new` и незнакомые ключи. Но запуск требует прав администратора из-за
драйвера WinDivert, а задание это запрещает. Нужен ручной прогон:

```
netzapret start --proxy-config runtime/singbox.json --preset "Universal V6"
```

Функциональной проверки у winws2 нет и быть не может: он не слушает портов
и не имеет API. Доступен только признак живости процесса.

## Пункт 3. Выборочный перехват — РЕАЛИЗОВАН, не тестирован вживую

Спецификацию реконструировать не пришлось: она записана в
`docs/coexistence.md` по итогам замера 2026-08-23. Реализовано именно так.

```
netzapret config --sub <ссылка> --proxy-only
```

**Задача.** Под поднятым TUN ломаются рецепты Zapret с поддельными пакетами:
трафик выходит переоткрытым сокетом sing-box, а WinDivert рассчитывает увидеть
исходный поток приложения. Замер показал: голый `multidisorder` (YouTube)
и `send + syndata` (Discord) туннель переживают, а `fake` (Google, Claude) — нет.

**Почему не исключениями.** Первой мыслью было вывести десинк-трафик из
туннеля через `route_exclude_address`. Разбор Universal V6 это опроверг:
из 20 секций с `fake` четырнадцать сопоставляются только по доменам,
а поле принимает лишь адреса. Прикрыло бы 5 из 20.

**Что сделано вместо.** Инверсия: не «исключить десинк», а «завести только
прокси».

1. Адрес fakeip выдаётся **только** доменам с правилом `mode: proxy`.
   Всем остальным отдаётся настоящий адрес.
2. У TUN стоит `route_address` из диапазонов fakeip плюс адреса резолверов
   плюс CIDR из правил `mode: proxy` по адресу.
3. Следствие: десинк-трафик туннеля не касается вовсе.

**Адреса резолверов заводятся в туннель намеренно** — иначе fakeip нечего
подменять: запрос не дойдёт до sing-box. Читаются из системы только на чтение,
настройки DNS не менялись. Правило `hijack-dns` в маршрутах стоит раньше
исключения приватных сетей, поэтому запрос к роутеру тоже перехватится.

Проверено `sing-box check`: конфиг корректен, `route_address` содержит
5 записей (два диапазона fakeip, три резолвера), правило DNS выдаёт fakeip
только `rutracker.org`. **Вживую не запускалось: TUN требует прав
администратора.**

Исключения по спискам пресета остались отдельным флагом `--exclude-preset`
для режима сплошного перехвата. При `--proxy-only` они избыточны, и ставить
7467 маршрутов ради страховки я не стал.

## Решения, принятые самостоятельно

**Git-репозиторий создан** (`git init`) — его не было, а задание требует
коммитов. Первый коммит зафиксировал состояние до ночной работы.

**Локальный инбаунд `mixed` для проверки прокси.** Формально это SOCKS/HTTP
на 127.0.0.1, от которого пользователь отказывался как от *режима работы*.
Здесь он используется только как испытательный стенд: без него проверить
транспорт вообще нельзя, потому что TUN требует прав администратора,
а их использовать запрещено заданием. В продукт это не попадает.

**Пробуются по одному серверу каждого протокола** по умолчанию, а не все:
этого достаточно, чтобы отличить «сломан транспорт» от «сломан конкретный
сервер», и не занимает четверть часа. Полный перебор — флагом `--all`.

**Три службы определения внешнего адреса** вместо одной: недоступность одной
службы иначе выглядела бы как неисправность прокси.

## Границы, которые соблюдены

Ничего из требующего прав администратора не запускалось: ни TUN, ни фильтры
WFP, ни системные маршруты, ни DNS, ни реестр. Все проверки прокси идут через

изменялись — только читались.
